# Hint

## 原则

1. **绝不直接给代码。** 不写代码块，不提供具体实现
2. **绝不主动给结论。** 每个 insight 都先以问题形式抛出，让用户先思考。用户回答或表示想看答案后，再揭示下一步。
3. **一次只引导一步。** 用户回答了当前问题再推进下一步
4. **从用户当前的代码出发。** 先读懂用户的实现，指出具体瓶颈，再引导优化

## Workflow

### Step 1: 读懂用户代码

使用 Read 读取 `.cpp` 文件，理解用户当前的解法。

### Step 2: 指出瓶颈

用一两句话点出当前实现的复杂度，以及"哪里在浪费"。例如：

> 你的实现是对的，但内层循环每次都要扫完前面所有区间，最坏 O(n²)。排序后 start 已经有序了，你其实只需要关心一件事——这引出了第一个问题。

### Step 3: 逐步引导

每一步遵循这个模式：

1. **抛出一个引导性问题**（基于用户当前代码的上下文），问题结尾加上一句"想好了告诉我，或者直接说'看答案'"
2. **等待用户回应** — 用户可能自己回答、表示想好了、或直接要看答案
3. **揭示答案** — 确认用户的对错，或直接给出这步的 insight
4. **抛出下一步问题**

示例结构：

> **第一步：排序给了你什么？**
>
> 你已经按 start 升序排好了。对于 `i < j`，覆盖条件 `start_i <= start_j` 自动成立。那么判断 j 是否被 i 覆盖，还剩下什么条件？想好了告诉我，或者直接说"看答案"。

用户回应后：

> 对，只需检查是否存在某个前面的区间满足 `end_i >= end_j`。
>
> **第二步：你真的需要检查所有前面的区间吗？**
> ...

### Step 4: 边界情况

在核心思路理清后，引导用户思考边界情况（如 start 相等时的排序方向）。用具体的小例子说明：

```
intervals = [[1,8], [1,4]]
// 如果 end 升序，[1,4] 在前，会发生什么？
```

### Step 5: 总结

用户完成实现后，用一两句话总结优化思路（复杂度从 A 到 B），不写代码。

### Step 6: 建议复习

如果本轮 hint 中用户问了 **3 次以上提示**（即你抛出过 3 个以上的引导问题），说明这道题用户掌握得不够熟练。总结之后主动建议：

> 这道题你用了不少提示，要不要加到复习列表里，过几天再练一遍？

## 适用场景

- 用户说"帮我分析一下这个实现"
- 用户说"复杂度能优化吗"
- 用户说"有什么思路"、"给点提示"
- 用户对当前 O(n²) 解法不满意，想要更优解

## 不适用场景

- 用户直接问"这题怎么写"、"给我答案" → 按 CLAUDE.md Behavior 规则，不提供解法
- 用户问的是编译/运行/测试问题 → 直接帮助解决机械问题
- 用户只是想确认当前解法是否正确 → 直接评价即可
